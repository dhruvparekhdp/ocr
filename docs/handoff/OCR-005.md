# Handoff OCR-005 — Indian invoice fields and validation

## Summary

`jarvis/OCR-005` was created from `main`. OCR-002 was already pushed on `jarvis/OCR-002`. This branch does not contain the OCR-001 CI workflow or the OCR-002 HTTP service. `main` has neither, and this ticket only adds GST extraction and checks on the existing classifier.

Invoice documents now extract GSTIN, PAN, HSN/SAC, taxable value, CGST, SGST (UTGST uses the same field), IGST, place of supply, and line totals, plus the invoice number, date, and total that were already extracted. `gstValidate.js` checks:

- GSTIN length, state code, embedded PAN shape, reserved `Z`, and the modulus-36 check character
- PAN shape (five letters, four digits, one letter)
- PAN versus the PAN inside the GSTIN
- invoice number and a real calendar date
- HSN/SAC as 4, 6, or 8 digits
- place of supply against GST state names and codes
- CGST equals SGST when either is charged, and CGST/SGST are not mixed with IGST
- place of supply versus the GSTIN state (intra-state versus inter-state)
- taxable value + CGST + SGST + IGST versus the invoice total
- parsed line totals versus the invoice total

The money tolerance is one rupee. Failures are `{ code, message }` warnings. Printed values are not replaced. A document with no GSTIN, CGST, SGST, UTGST, IGST, HSN, or SAC is left alone, so the existing non-GST sample invoice stays quiet.

Synthetic invoices are in `fixtures/gst-invoices.json`. `npm test` also writes them as wide text PDFs so a GST line is not wrapped away from its line total.

## Assumptions

- Branch from `main` was possible. GST work is on the CLI and upload pipeline, not on `POST /v1/extract` from OCR-002. When that branch merges, the service will not see these warnings unless it calls `analyzeText` or the same validator.
- Invoice number, date, and total reuse `documentNumber`, `date`, and `amount` via a `role`, instead of a second copy of those fields.
- Numeric dates that could be either day-first or month-first are read day-first.
- A labeled PAN is kept even when it is invalid. The PAN inside the GSTIN is used only when no PAN label is present.
- UTGST is stored in the SGST field. Both are the local half of an intra-state split.
- Missing GST warnings are skipped unless the text contains GSTIN, CGST, SGST, UTGST, IGST, HSN, or SAC.
- The check character was checked against the published example `27AAACR5055K1Z7`. That string is only a test vector. Fixtures use `27ABCCE1234F1Z2`.
- Line items must be printed as `HSN … Taxable … CGST … SGST … IGST … Line Total …` on one line. Other table layouts are not parsed and do not get a silent total correction.

## Known gaps

- Checksum validity is not proof the GSTIN is registered.
- HSN is checked for length only, not against the tariff.
- A wrapped PDF line can split the line-total pattern. The sample generator uses a wide page. Real invoices with narrow wrapping can warn `line_unparsed` or miss the line.
- The batch CLI still has no per-field confidence score.
- The scanned sample receipt still OCRs `RCPT` imperfectly. That behavior was already on `main` and was not changed.

## Security impact

No new network calls, credentials, or stored uploads. Validation reads text already extracted in memory. Warnings include the printed GSTIN or PAN from the document so a reviewer can see which value failed. Synthetic fixtures are not real registrations.
